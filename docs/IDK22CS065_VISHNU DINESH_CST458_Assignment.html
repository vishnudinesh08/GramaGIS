  • Previous features rechecked manually after modifications

  • Bug fixes could introduce new errors because modules are tightly connected
  • No regression checklist maintained
  • No automated regression suite available

Part C - Testing Approaches Used

11. Black Box Testing Practices

  • Input-output testing done for login, feedback, search, map data load, and downloads
  • Valid and invalid credentials, categories, wards, layers, and statuses were tried
  • Boundary checks considered for longitude, latitude, ward parsing, and login attempt limits
  • Invalid conditions tested using empty fields, wrong token, incomplete coordinates, and unsupported actions
  • Examples: invalid login rejection, invalid feedback coordinates rejection, unsupported layer rejection

12. White Box Testing Practices

  • Code-level logic checked manually while debugging
  • Conditions, branches, and loops checked in auth, feedback validation, role checks, and proxy logic
  • Internal paths checked for timeout, invalid token, missing env, and invalid GeoServer response cases
  • Exception handling paths were also verified informally
  • Examples: login rate-limit branch, status normalization logic, WKT-to-GML conversion path

13. Grey Box Testing Practices

  • Testing done with partial internal knowledge of routes, schema, database behavior, and roles
  • API structure and database knowledge helped identify errors faster
  • Both UI behavior and internal workflow were used during testing
  • Examples: checking UI search against backend query behavior, checking feedback status persistence, checking schema-driven admin editor

Part D - Evaluation and Improvements

14. Gaps in Existing Testing Process

  • No formal test planning
  • No documented test cases
  • No automated unit testing
  • No automated integration or regression testing
  • Weak performance and stress testing
  • Limited acceptance testing with real users
  • Missing coverage for some edge cases and external failures
  • No defect tracking tool used
  • Time and coordination constraints reduced testing depth

15. Suggested Improvements

  • Add unit tests for validation logic, auth, query parsing, and XML generation
  • Add integration tests for login, feedback, query, and admin CRUD workflows
  • Prepare a system test checklist before release or demo
  • Perform formal acceptance testing with guide and real target users
  • Maintain a regression checklist after every major update
  • Document test cases with valid, invalid, and boundary inputs
  • Use automation tools such as Jest, Supertest, and Playwright
  • Improve usability and performance testing with structured observation and load tools
  • Use proper defect tracking and retesting records

16. Final Reflection

  • Manual functional, integration, and system testing were done reasonably well
  • Formal planning, documentation, automation, and load testing were insufficient
  • Test design and acceptance planning should have started earlier
  • Better testing would improve reliability, usability, and overall project quality
